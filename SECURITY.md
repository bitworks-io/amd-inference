# Security policy

FastLLM is Preview software and is not suitable for untrusted network exposure.

## Safe defaults

- The server binds to `127.0.0.1` only.
- Browser CORS is explicitly restricted to llama.cpp's special `localhost` origin policy and credentials are disabled; by default FastLLM has no API key and is not an isolation boundary against other processes in the same user session.
- An optional API key (off by default; `settings -ApiKey on`) makes the server refuse requests without it. The key is 32 random bytes, stored only under Windows per-user protection (DPAPI) in `api-key.dat`, passed to the server through its environment and never on its command line, and absent from `settings.json`, `status`, the run log and the support bundle. FastLLM refuses to start when the key is on but cannot be read, proves with a 401 and a 200 that the server enforces the key before anything says it is on, and sends the key only to its own server process on 127.0.0.1. Limits: any program running as the same Windows user can read the key (it can ask Windows to unprotect it, or read the server's memory); the key is plain text in each client's own settings once you paste it there; llama-server's key comparison is not constant-time, which does not matter for a 256-bit key on loopback; the key adds no encryption, so loopback traffic stays readable by an administrator; and while FastLLM is not running (after a stop, a crash or the idle stop) any program on the PC, including one under another Windows account, can listen on FastLLM's port, and an app that keeps calling that port then sends its key to that program. FastLLM checks who is listening before and after each of its own keyed requests and stops with `api-key-listener-changed` if the listener changed in between, but it cannot check on behalf of your apps. If an app may have called the port while FastLLM was stopped and another program was listening, create a new key (`settings -ApiKey rotate`, or Create a new key in Settings); the old key then stops working at the next start. The copy buttons keep the key out of the Windows clipboard history and the cloud clipboard, but the key stays on the clipboard until you copy something else.
- An optional embeddings server (off by default; this release lists no embedding model, so it cannot be turned on yet) is a second llama-server child of the same supervisor, started only after the model is Ready. It binds `127.0.0.1` only, on its own port (default 8081), and gets the same scrubbed environment, empty per-run configuration roots and kill-on-close job as the model's server; it runs on the CPU (`--device none --n-gpu-layers 0`, and it is reported ready only when the engine's own output shows the model on the CPU) with `--offline`, `--no-agent` and `--no-ui`. With the API key on it receives the same key through its environment (never its command line), must pass its own 401/200 check before it is reported ready, and is sent the key only after the listener on its port is confirmed to be that process (its proof uses `/props`, as the model's does; the engine answers its model list without a key). Embedding inputs are treated like prompts: its engine output is discarded after the start check, which embeds a fixed built-in sentence, and nothing from a request, a document or a vector is written to the status, the run log or the support bundle. A failure of the embeddings server never stops or changes the model, with one exception: if the listener on its port can no longer be confirmed right after a request with the API key was sent, the key may have been seen, so FastLLM stops as it does for the model's own port and asks for a new key.
- Vulkan is the engine on other cards and the fallback on the RX 7900 XT and XTX, where HIP is the default: its two components (the llama.cpp HIP engine from github.com and the AMD ROCm runtime from stable.repo.amd.com) are downloaded from those official sources to the user's PC, only after license consent or the opt-in automatic setting, and are checked against pinned sizes and SHA-256 hashes. Bitworks does not sign or redistribute them. The Vulkan setup requires a working AMD Vulkan driver and Microsoft VC++ 2015–2022 x64 runtime. Before native execution, FastLLM checks for the three imported VC14 DLL filenames and `vulkan-1.dll` in System32 and requires a 64-bit process; the isolated probe must then return an adapter whose reported name passes an AMD/discrete heuristic. File presence and name matching do not attest prerequisite versions, signatures, architectures, loader vendor, or PCI vendor identity. FastLLM never installs the Vulkan driver; it offers the Microsoft VC++ runtime only after showing a review, and installs it only when the user clicks, under Windows' own prompt. The cataloged ROCm b10698 archive is not downloaded or run because its imported `hipblas.dll` is absent.
- The resolver refuses to deliberately select CPU and requests all GPU layers. Readiness requires the engine's full layer-count and selected GPU-buffer report. That report is not proof of every operation's placement, dedicated-memory residency, or absence of WDDM paging/spill.
- Engine and model artifacts use immutable URLs, expected lengths, a live download-size ceiling, and SHA-256 verification. Interrupted downloader children are terminated before the destination lock is released. The exact extracted Vulkan manifest detects undeclared files even when hidden, rejects reparse points, and is reverified before probe and start; the complete model hash is reverified on every start.
- First acquisition of an exact model artifact requires interactive approval or an explicit `-AcceptModelLicense`. Approval writes a receipt bound to the exact upstream license revision and artifact digest. That matching receipt can authorize unattended reuse or repair of the same artifact; it never transfers to a changed revision or digest, and start rejects a missing or mismatched receipt.
- Heterogeneous and tensor-parallel GPU modes are not automatically enabled.
- Install, live planning/detection, doctor, and start reject administrator execution and use a per-user data root. Only an offline `plan -HardwareFile ...` may run elevated, and fixture injection cannot reach an executing action.
- No telemetry is sent. The update check makes one unauthenticated request to the GitHub releases API at most once a day, sends nothing beyond that request, and can be turned off in settings.
- No automatic telemetry upload is enabled. Explicit lab diagnostic/benchmark tools can write private local reports; review and sanitize them before sharing. No prompt logging is enabled by this project.
- Native probe/server children receive empty per-run `%APPDATA%`/`%PROGRAMDATA%` roots, a restricted executable search path, and no inherited `LLAMA_*`, `GGML_*`, `VK_*`, `HIP_*`, `ROCM_*`, `HSA_*`, `ROCBLAS_*`, `SMITHY_*`, `AIP_*`, `HF_TOKEN`, or `MTMD_BACKEND_DEVICE` overrides. The server is API-first; an optional local chat page is off by default. It also passes `--offline`, `--no-mmproj`, `--spec-type none`, `--no-agent`, `--host 127.0.0.1`, and `--no-ui`; `--no-ui` is omitted only when the user turns the local chat page on, and `--no-agent` and the loopback host stay, so there are no built-in tools. `--no-agent` disables the built-in tools and the CORS/MCP proxy, and FastLLM never passes `--mcp-servers-config`.
- One install/start operation owns each InstallRoot's exclusive file lock. Status is advisory local state, not trusted authorization. Stop requests name a run; the owning supervisor terminates its own process instead of trusting a stored PID. Recovery history never grants model consent, skips hashing, or authorizes a download. An explicit model selection cannot be replaced by recovery.
- The server/control-window process wrapper uses a kill-on-close Windows Job Object and captures bounded startup output in memory. After readiness, it discards engine output rather than writing request logs. Benchmark/soak exports contain measurements and diagnostics, not generated text. Same-user process access and crash dumps are outside that privacy boundary. Native Windows containment still requires validation.
- The readiness HTTP client accepts literal IPv4 loopback only, ignores proxies, refuses redirects, bounds responses, and enforces whole-request deadlines. An occupied-port preflight reduces accidental checks against another service, but a bind race remains. There is no authenticated private listener/gateway: clients must wait for Ready, and local processes are not isolated from one another.
- Releases are Authenticode-signed by Bitworks LLC (see Release signing), and `fast-llm.ps1 doctor` verifies the installed files against the signed catalog. The launcher (`FastLLM.cmd`) adds `-ExecutionPolicy RemoteSigned` for its own PowerShell process only when the effective policy is `Restricted` or `Undefined`; it never weakens `AllSigned` or Group Policy, disables security products, or configures remote access.

Do not change the host to `0.0.0.0` without adding authentication, restrictive CORS, firewall consent, and TLS or a trusted reverse proxy.

## Release signing

Installers are signed with Microsoft's Azure Artifact Signing and carry a timestamp. FastLLM accepts a signature only when all of these hold:

- The signer's organization is Bitworks LLC (`O=Bitworks LLC`).
- The chain ends at the Microsoft Identity Verification Root Certificate Authority 2020, thumbprint `F40042E2E5F7E8EF8189FED15519AECE42C3BFA2`.
- The leaf certificate carries both required EKUs: `1.3.6.1.4.1.311.97.1.0` and `1.3.6.1.4.1.311.97.990689314.800187930.133508941.234438932`.
- A certificate that is outside its validity period (`NotTimeValid` or `NotTimeNested`) is tolerated only when the signature carries a timestamp. A certificate that is still valid needs no timestamp.

The pins live in `src/FastLlm.Trust.ps1`.

## Update security

FastLLM checks for updates once a day, with one unauthenticated request to the GitHub API, and never installs without a click. Before an update runs it passes these six steps, and any failure stops it:

1. The server is stopped and confirmed stopped.
2. `SHA256SUMS` is downloaded (size-capped) and parsed strictly.
3. The installer is downloaded from the release and its SHA-256 and size must match.
4. The installer's signature must pass the pins above.
5. The installer's ProductVersion must equal the release version and be newer than the installed one.
6. The per-user installer runs, then the installed files are checked for integrity.

Download URLs must come from the project's GitHub release assets. `fast-llm.ps1 doctor` reports `installIntegrity` at any time.

### Reinstall the previous version (explicit, one step)

A normal update never installs an older release. `fast-llm.ps1 update -Previous` (and the window's **Reinstall previous version** button, shown only when it is allowed) goes back exactly one version, only after a confirmation that names both versions, and never automatically (`-Unattended` is refused). The target is the release the installer recorded as installed just before this one; no remote answer picks it. It is refused when a newer release exists, when the target is below the installed release's `rollbackFloor` (a known security problem), when the two releases declare different data formats, or when the record is missing or does not match this install. The target is fetched by exact tag from the project's published release assets and passes the same six steps as an update (stop, `SHA256SUMS`, size and SHA-256, pinned signature, exact ProductVersion, integrity), with the one difference that the release must be the recorded one and older. The window decides whether to show the button from the daily update check only, with no extra request; the release page is checked for the exact target when you click, and the action is refused if update checks are turned off, because a newer release could not be ruled out. Deleting a release's assets from the release page turns this off for that version. The record is cleared after a reinstall, so going back never chains.

## Reporting

Do not open a public issue for a vulnerability that could expose local files, execute code, bypass artifact verification, or expose the inference API. Until Bitworks publishes a dedicated security address/process, contact the repository owner privately. A public GA release is blocked on publishing a complete coordinated-disclosure contact and response policy.

## Supply-chain expectations

Releases include a signed installer, `SHA256SUMS`, an SBOM (`.cdx.json`) and `THIRD_PARTY_NOTICES.md`. Hash checks alone do not authenticate the publisher; the signature pins above do. The updater accepts only the signed installer for a newer release and has no privileged arbitrary-command path.
